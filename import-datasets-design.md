# Dataset Import Design: Cross-Project / Cross-Instance + Multi-Source Portability

## Goal

Design a feature to import datasets from multiple sources, starting with datasets exported from this application, and preparing for external formats.

This document captures:

- further requirements discovered from codebase research,
- a practical implementation plan,
- open questions we need to resolve before implementation.

Roadmap intent:

1. **Initial support:** import ZIP exported by this application.
2. **Next:** import LeRobot v2/v3 datasets.
3. **Later:** import datasets generated by Trossen SDK.

---

## Current State (Research Summary)

### What exists today

- Datasets can be **downloaded as ZIP** via backend API (`GET /api/dataset/{id}/download`).
- Dataset ZIP export currently zips the whole dataset directory (no explicit app-level manifest).
- Datasets are represented in DB with fields including `id`, `project_id`, `environment_id`, `name`, `path`, `default_task`.
- Dataset on-disk format is LeRobot-style (`meta/info.json`, `meta/stats.json`, episodes, parquet chunks, videos, etc.).

### What does not exist yet

- No dedicated **dataset import endpoint**.
- No explicit import workflow for ID remapping, compatibility validation, or conflict resolution.
- No end-to-end integrity checks (manifest + checksum) for portable import packages.

### Key constraints inferred from current architecture

- `project_id` / `environment_id` are instance-local UUIDs and are not portable by default.
- `path` handling is sensitive to storage layout differences between instances.
- Dataset schema/feature compatibility must be validated before linking to a target project/environment.
- Large archives require careful handling (size limits, temp storage, async processing).

## Requirements for Import Feature

## 1) Functional requirements

1. User can upload an exported dataset ZIP into a target project.
2. System validates archive structure and dataset format before commit.
3. System creates a new dataset record with a new local dataset ID (default behavior).
4. System maps/reconciles target `environment_id`.
5. System supports conflict handling for dataset naming/path collisions.
6. User receives clear status and errors (invalid archive, incompatible schema, size exceeded, etc.).
7. System must detect source format automatically (app-export, LeRobot v2/v3, Trossen SDK as adapters are added).
8. Import must be a staged workflow: upload/detect → review/edit metadata → finalize import.

## 2) Compatibility requirements

1. Validate LeRobot format/version compatibility (`meta/info.json` + expected file layout).
2. Validate feature schema compatibility with target environment/robot config.
3. Define behavior for unsupported versions/codecs/feature mismatches (block, warn, convert).
4. Normalize source-specific metadata into a canonical internal Dataset Manifest.

## 3) Integrity & safety requirements

1. Verify archive integrity (checksum) before import finalization.
2. Safe extraction with path traversal protection.
3. Enforce max upload size and max uncompressed size.
4. Import should be atomic (staging area + commit/move on success only).

## 4) Data-model requirements

1. Imported dataset gets local IDs (dataset + environment mapping policy).
2. DB and filesystem remain consistent under failures.
3. Path storage strategy is stable across environments (prefer storage-root-relative paths).

## 5) UX requirements

1. Upload + progress + final result UI.
2. Pre-import validation report (compatibility checks).
3. Actionable remediation guidance on failure.
4. A second-step review form where user can attach/select environment, set dataset name, and fill missing metadata before final commit.

## 6) Operational requirements

1. Support large datasets without blocking request thread (background job likely required).
2. Auditability: who imported what, when, into which project.
3. Observability: logs/metrics for import duration, failures, size, validation reasons.

## 7) Extensibility requirements

1. Source adapters should be pluggable and independently testable.
2. New source support should not require redesigning the import UX.
3. Canonical manifest schema must remain stable with versioning.

## Proposed Design Direction

## A. Use a canonical Dataset Manifest generated at import time

Introduce an internal canonical manifest (e.g., `dataset-manifest.v1.json`) that the system uses regardless of source format.

Purpose:

- unify metadata coming from different sources,
- provide a stable contract for validation and UX,
- allow incomplete manifests with `unknown` fields for user completion in step 2.

Suggested canonical fields:

- `manifest_version`
- `source_type` (`geti_export`, `lerobot_v2`, `lerobot_v3`, `trossen_sdk`, `unknown`)
- `source_format_version`
- `dataset_name`
- `default_task`
- `robot_configs[]` (robot type, arm/joint naming hints)
- `camera_configs[]` (camera id/name, resolution if known)
- `fps`
- `feature_schema_hash`
- `episode_count`, `frame_count`
- `warnings[]` and `missing_fields[]`

## B. Add source detection + adapter pipeline

Pipeline:

1. Upload ZIP
2. Detect source structure
3. Route to source adapter parser
4. Produce canonical Dataset Manifest + compatibility report
5. Persist a draft import job state for UX step 2

Adapter strategy:

- `GetiExportAdapter` (initial release)
- `LeRobotAdapter` (v2/v3 support)
- `TrossenSdkAdapter` (later)

## C. Introduce a staged import job model (intermediate steps)

Extend job schema with a dedicated import type and step-level progress.

Proposed `JobType` addition:

- `DATASET_IMPORT = "dataset_import"`

Proposed staged lifecycle:

1. `UPLOADING_ARCHIVE`
2. `DETECTING_SOURCE`
3. `GENERATING_MANIFEST`
4. `WAITING_FOR_USER_INPUT`
5. `VALIDATING_FINAL_CONFIGURATION`
6. `EXTRACTING_AND_REGISTERING`
7. `COMPLETED` / `FAILED` / `CANCELED`

Proposed payload shape (new model in `application/backend/src/schemas/job.py`):

- `project_id`
- `uploaded_archive_path` (or object-store key)
- `detected_source_type`
- `draft_manifest`
- `validation_report`
- `user_overrides` (dataset name, selected environment, missing metadata)
- `final_dataset_id` (set on success)

This aligns with the two-step UX: detect/manifest first, user confirmation second.

## D. Add explicit export/import manifest for app exports

Add app-level manifest inside archive (e.g., `geti-dataset-manifest.json`) to complement LeRobot metadata.

Suggested fields:

- `manifest_version`
- `exported_at`
- `source_app_version`
- `dataset_name`
- `default_task`
- `lerobot_codebase_version`
- `robot_type`
- `feature_schema_hash`
- `episode_count`, `frame_count`
- checksum metadata

Why: ensures portable, explicit contract for import checks and future migration paths.

## E. Add import API + job flow

Introduce endpoint (shape TBD), likely project-scoped, e.g.:

- `POST /api/projects/{project_id}/datasets/import`

Workflow (v1):

1. Upload archive + create dataset-import job
2. Stage archive to temp storage
3. Detect source + generate canonical manifest
4. Return draft manifest + required user input fields
5. User submits finalize request (name/environment/overrides)
6. Validate finalized configuration
7. Extract into final dataset directory
8. Create DB record
9. Return imported dataset ID / job status

Prefer async job for large uploads.

## F. Define mapping/conflict policies

- **ID policy:** always mint new local dataset UUID.
- **Environment policy:** map by compatibility rules, optionally create new environment.
- **Name conflict policy:** reject, rename, or merge (merge likely out of initial scope).

## G. Harden extraction and commit semantics

- Reject unsafe archive entries.
- Validate declared vs actual checksums/sizes.
- Use staging directory + atomic move.
- Roll back DB writes on extraction/validation failure.

## H. Version compatibility strategy

- Define supported range for dataset format versions.
- Start strict (block unsupported) with explicit error messages.
- Add migration/conversion hooks later if needed.

## Phased Implementation Plan

## Phase 0 — Design + API contract

- Finalize canonical dataset manifest schema v1.
- Finalize import endpoint contract and response model.
- Define staged job model and intermediate states in `schemas/job.py`.
- Decide sync vs async import (recommend async with job polling/events).
- Finalize conflict and environment mapping policies.

Deliverable: approved design + OpenAPI updates.

## Phase 1 — Backend MVP (safe import, app-export source only)

- Implement archive upload + staging.
- Implement source detection framework with `GetiExportAdapter`.
- Implement validation pipeline:
  - archive safety checks,
  - required file layout checks,
  - source-specific parse + canonical manifest generation,
  - manifest/checksum checks,
  - compatibility checks.
- Implement dataset creation with local ID remapping.
- Implement two-step finalize endpoint (user-provided name/environment/metadata).
- Return clear structured errors.

Deliverable: API import works for compatible app-export archives via staged job flow.

## Phase 2 — UI staged flow

- Add “Import dataset” entry point in dataset/project UI.
- Add upload progress + source detection status.
- Add manifest review/edit step (attach environment, dataset name, fill blanks).
- Add success and failure flows with next actions.

Deliverable: user-complete workflow from UI.

## Phase 3 — Source expansion: LeRobot v2/v3

- Add `LeRobotAdapter` (v2 + v3 detection/parsing).
- Normalize LeRobot metadata to canonical manifest.
- Define/implement compatibility warnings and blocking conditions.

Deliverable: staged import supports direct LeRobot datasets.

## Phase 4 — Robustness and scale

- Background job orchestration + polling/status endpoint.
- Size/time limits and admin-configurable thresholds.
- Import audit logging and metrics dashboards.

Deliverable: production-grade import behavior.

## Phase 5 — Source expansion: Trossen SDK + enhancements

- Add `TrossenSdkAdapter` detection + parsing.
- Map Trossen-specific metadata into canonical manifest.
- Add source-specific validation guidance in UI.

- Optional merge mode.
- Optional format conversion/migration support.
- Potential interoperability with external dataset hubs.

---

## Out of Scope (initial release)

- Full system restore (DB + storage volume backups).
- Model lineage reconstruction across instances.
- Automatic transcoding/conversion for incompatible media/codecs.
- Dataset merge/reindex semantics (unless explicitly prioritized).
